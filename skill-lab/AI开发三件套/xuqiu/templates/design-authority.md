# 设计权威抽取清单 —— 设计定稿后、拆 ticket 前必跑

> **触发时机**：关键页面的设计方案（`design-options.md`）已选定、设计工具的交接包已回来。
> **这一步在治什么**：设计定稿 ≠ 设计权威。交接包是给人看的（截图 + 一份手写交接文档），
> 不做结构化抽取就直接拆 ticket，会有两类东西**静默漏掉**，到实现期才炸：
> ① 稿上那些"会变的内容块"没人把它们回流成需求/字段；② 被否决方向的稿混在同一个目录里当 ground truth 被误用。
>
> **产出**：填满的 UI 权威索引（`authority/ui-index.yaml`）+ **回流出的新 REQ / 新字段** + 误导料标记。
> **判据**：拆 ticket 的人只看 UI 索引就知道"这页锚哪张图、用哪些组件、每块数据从哪来"。

---

## A. 材料分级（先标坑，再用料）

交接包里**混着被否决方案的稿**是常态（同一个画布导出，文件名往往只差一个字母）。不标出来，实现期一定有人拿错。

| 等级 | 含义 | 怎么处理 |
|---|---|---|
| 🥇 ground truth | 选定方向的定稿截图 / 可现截的源文件 | 登记进 UI 索引，每页锚到具体文件 |
| 🟡 衍生可信 | 设计师手写的交接文档（token 表、组件清单） | token 值可信；**组件清单默认不全**，见 C |
| 🟡 衍生 | 原型实现代码（jsx/html） | 结构可参考，**里面的内容是假数据** |
| ❌ 误导 | **被否决方向的稿** / 跨方向的画布总览 / 分辨率不足的缩略图 | **逐个列出来 + 写明为什么是坑**，不能只是"不提它" |

> 一张图同时含两个页面（画布截图跨页）时，在索引里写清"左半 / 右半"，别整张当一页。

## B. Design Token（每个主题一套完整变量）

- [ ] 颜色：背景 / 次级面 / 主文字 / 次文字 / 弱文字 / 分隔线 / 边框 / 强调色
- [ ] **每个主题（light / dark / …）都要有完整一套**，变量名集合必须**完全相同**
- [ ] 字体族 + 字号阶 + 字间距
- [ ] 间距 / 圆角 / 阴影的基本尺度（"圆角=0"这类也要显式写，否则实现层会自己加）
- [ ] 响应式断点 + 每个断点下的变化
- [ ] 语义色（状态徽章 / 分类徽章）—— 每个枚举值一个色，**与 schema 的字典值对齐**

**硬约束（写进验收断言）**：组件内**零颜色字面量**，全部走变量。
> 没有这条，换主题 = 逐个组件翻改；有了这条，换主题 = 改一个文件的变量值。
> **设计只交付了一套主题、而需求要两套时**：工程侧按选定方向的语言推导另一套，标 ⏳ 待签字，
> 并把签字点排进具体某一天（出真截图给人看），不要拖到上线前。

---

## C. 组件全集（★ 不要抄设计师给的清单）

设计师交接文档里的组件表**几乎必然是不全的** —— 它列的是"设计时画过的组件"，
漏掉的通常是：**语言切换、主题切换、状态徽章、统计/元数据条、空状态、加载态**。

- [ ] **逐页扫一遍截图**，把每个重复出现的视觉单元登记成组件
- [ ] 与设计师清单对比，**补齐差集并注明"稿中无，按选定方向语言自拟"**
- [ ] 每个组件写清：用途 + 关键视觉要点 + 数据来源

---

## D. ★ 内容块回流（这一步最容易漏，漏了必返工）

> **稿上每一个"会变的东西"都是一条需求。** 逐页逐块过一遍，问三个问题：

| 问题 | 如果答案是… |
|---|---|
| 这块内容**会不会变**？ | 不变 → 界面固定文案，进前端字典，不进 DB |
| **谁**改它？ | 使用方自己改 → **必须有后台入口 + 存储字段** |
| 它的值**能不能算出来**？ | 能算（计数 / 汇总）→ **禁止手填**，标记为自动计算字段 |

**产出**：一张表，逐块登记 → 直接变成新 REQ / 新字段。

| 页面 | 内容块 | 会变? | 谁改 | 落到哪 | 备注 |
|---|---|---|---|---|---|
| `<页>` | `<块，如 Hero 右栏 4 项>` | Y | 使用方 | `<表.列 / 新表>` | `<是否自动算>` |

**这一步的三条铁律**（都是被真实漏项打出来的）：
1. **形状相同的小块合并成一张通用表**（如"标签+值+排序"的元数据条、卡片组），别为每组建一张表 —— 后台会多出几个几乎一样的列表页。
2. **稿上的数字（"共 18 项""5 个类型"）一律回原始料核对**，且**不准手填也不准前端写死** —— 数据增减后没人会记得改，官网从此显示错数。用自动计算字段。
3. **详情页的元数据格**（客户 / 周期 / 角色…）常常比列表页多出字段 —— 回原始料查这些字段存不存在，别只按列表页建模。

## E. 稿 vs 需求的冲突登记

设计过程中被口头砍掉/改掉的东西，**书面需求里往往还留着**（反之亦然）。逐条登记，走变更记录。

| # | 需求文档说 | 稿实际是 | 以哪个为准 | 处理 |
|---|---|---|---|---|
| 1 | `<如：深浅两套主题>` | `<如：只交付了浅色>` | `<需求>` | `<补推导 + 排签字点>` |

## F. 交付判据

- [ ] UI 权威索引每页一行，锚到 🥇 具体文件（含"左半/右半"这类定位）
- [ ] 误导料逐个标出且写明为什么是坑
- [ ] 每主题 token 完整且变量名集合一致
- [ ] 组件全集 ≥ 设计师清单，差集已注明来源
- [ ] **D 表逐块过完，回流出的新 REQ / 新字段已并入需求清单并重跑 `coverage_lint`**
- [ ] 冲突登记表清零（每条都有"以哪个为准"）

> **最后一条是回环**：设计回流会**产生新需求**。产出新 REQ 后必须回到需求清单重跑覆盖率校验，
> 否则这些从稿里挖出来的需求永远不在 ticket 里。

---

## G. micro 档（`meta.scale: micro` 时的收缩规则，2026-08-17）

小产品（预估 ticket ≤10 或 ≤3 天）不付全量仪式，但**内容块回流一步不减**——
它就是静态产品的需求主体（会变的说明文案 / 依据公告号 / 更新日期，全是字段）。

| 环节 | full | micro |
|---|---|---|
| ★ 内容块回流（§D） | 全量 | **全量（不减）** → 新 REQ 照常并入 + 重跑 coverage_lint |
| token 抽取（§B） | 每主题一套完整变量 | 单主题 + 页面 ≤3 时**跳过**（组件直接写，不建 token 层） |
| 组件全集扫描（§C） | 逐页扫 | 同上条件**跳过** |
| 误导料标记（§A）/ 冲突登记（§E） | 全量 | 保留（成本本来就低） |
| §F 判据 | 全表 | 只查两条：内容块回流出的 REQ 已并入清单；冲突登记清零 |
