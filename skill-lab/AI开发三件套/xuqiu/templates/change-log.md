# 变更记录（CR / Change Request）—— 决策终局的留痕层

> 2026-08-17 换版：以 一个实战项目`doc/changes.md`（实战版）为基线 + 「范围归属」列。
> 旧四列版没有一列是量、没有签字——自称「让返工成本可见」「下个项目报价的证据」
> 但两个真实项目的 CR 台账都证明了空洞。
>
> **需求正文一旦冻结 = 只读**。任何需求 / AC / 字段 / scope 变更走 CR，按时间倒序
> **append-only** 追加（旧 CR 不改）。AI §0 自检强制扫本文件：涉及当前 ticket 的
> CR → **以 CR 为准**（CR 覆盖需求正文）。
>
> 拍板落点联动：CR 拍板的口径同时写回 REQ 的 `decided_by/at/cr/text_sha` 四字段
>（coverage_lint 盯「已拍板口径被改动未走 CR」）；架构级口径另立 ADR 并互相引用。

---

## CR 模板（复制整段填空，贴到「CR 列表」最上方）

```
## CR-YYYYMMDD-NN: <一句话变更标题>

- **提出人**：<负责人 / 甲方 / Reviewer / AI 评审>
- **范围归属**：合同内 / 合同外 / 自定范围内 / 自定范围外   ← 必选枚举。
  「合同外」的活 = 加钱或换掉等量范围，这一列攒起来就是下次报价的证据；
  solo 项目选「自定范围外」= 触碰了 out_of_scope，先把 deferred REQ 改回来
- **影响 ticket**：<id1>, <id2>（无则写"无新增，仅确认现状"；
  不手数——粘 `authority_lint.py impact` 的输出，手填必漏且漏掉无声）
- **背景**：<为什么要改——甲方改了 xlsx / 实测撞墙 / 评审发现不一致>
- **变更前**：<引用被冻结正文的原段 或 ticket 原 AC>
- **变更后**：<新内容，能落地的具体值>
- **影响下游**：<连带改的表 / 字段 / 文档 / 其他 ticket，没有就省略>
- **决策**：✅ 接受 / ❌ 拒绝 / ⏸️ 待定
- **签字**：<谁> @ YYYY-MM-DD（<决策依据一句话；可附回退条件>）
```

> **铁律**：
> 1. **before/after 都要有**——只写"改成 X"不写"原来是什么"，没人看得懂为什么。
> 2. **必须有签字**——CR 是有人拍板的决策，不是 AI 自己改的笔记。签字人 = REQ
>    decided_by 的合法取值（永远是人）。
> 3. 甲方原始材料 vs 推断设计冲突时，**甲方原始材料优先**，CR 里点明以哪份为准。
> 4. 改完权威/需求必须跑 `authority_lint.py diff → impact`，受影响 ticket 置 stale
>    ——跳过 impact 直接 snapshot = 把变更悄悄吞掉。
