# 任务计划（task plan）—— `/xuqiu` 在需求层产出，`/zhixing` 按此串行跑

> **任务（daily）= 多个 ticket 的集合**。把全部 ticket 编成任务 D1-Dn，归属写进每个 ticket
> front-matter 的 `phase` 字段（**必填**，漏写会被静默跳过）。
> `/zhixing` 按任务顺序串行：先派 impl subagent（每 ticket 一个）实现 + 各自跑 accept，
> 再派**一个干净 QA subagent**（全新上下文）跑完整 L0-L3 + 返工循环，全绿才进下一个任务。
> 本文件是"人看的任务总览 + 每个任务的 QA 范围"。

## 粒度

```
需求点 REQ ──→ ticket（功能点）──→ 任务 daily（本文件编的）──→ 项目
                    │                      │
              accept 2-3 条          完整 L0-L3 QA 门
```

**完整测试只在任务边界做**——每个 ticket 都拉完整 QA 是把成本乘以 ticket 数，
且单 ticket 的时间窗测不出跨 ticket 的集成问题（那正是任务级 QA 门的价值）。

## 编任务的原则

- **一个任务 = 一个可独立验收的里程碑**（不是按天数切，是按"做完能测出一段完整链路"）。任务数随项目定。
- **同任务内的 ticket 尽量弱耦合**（touches 不冲突就能并行实现）；**跨任务是硬前置**（Dn 依赖 D<n 的产物已就绪且已过 QA 门）。
- **`depends_on` 不许跨到后面的任务**——依赖只能指向本任务内或更早任务的 ticket。指错了 `/zhixing` 会报 `action=blocked`，说明任务划分错了。
- **每个任务必须写得出 QA 范围**：这个任务完了，QA subagent 要测什么（哪些链路/对账/端侧页面）。**写不出 = 任务切得不对**，回去重编。
- 任务大小建议 3-8 个 ticket：太小则 QA 门开销占比过高，太大则出问题时返工面积大。

## 每个任务末的 QA 门（`/zhixing` 自动执行，人只在任务末抽验）

一个**干净 QA subagent**（**不读实现方的 report / 解释 / 自评**，只拿 ticket + 蓝图 + 原型 + 该任务 QA 范围）跑：

1. **代码**：编译 + 单测（真门是 build，不是类型检查）
2. **脚本**：真实 seed 数据上的跨表对账 / 接口断言（禁自造数据自证）
3. **端侧/真机**：admin 截图断言 / 移动端 H5→设备自动化→真机（命中高危 pattern 强制真机）
4. **独立邪路**：跨日期边界 / 非超管权限 / 空数据 / 同日区间 / 并发，每类至少 1 条

有问题 → 返工循环（问题派回 impl subagent 修 → **重跑整个 QA 门**，回归才是重跑的意义）直到本任务全绿
→ `task_state.py set --phase D<N> --status qa_passed` → 进下一个任务。
**真机长尾仍需人偶尔抽验**（模型天花板，不假装能全自动）。
