# 设计方案模板 —— 关键页面出 2-3 个方案交 负责人 审选

> 触发时机：**需求/蓝图三件套确定后、拆 ticket 前**。针对关键页面（一级导航主页 / 高频录入页 / 看板 / 复杂交互）各出 **2-3 个设计方案**给 负责人 审。
> **负责人 定：需求确定后必须先出 2-3 个设计方案回来审核，选定后才进 ticket 拆解。** 不选定不拆 —— 视觉定不下来就拆 ticket，等于让实现层去猜 UI，返工的根。
> **视觉权威源 = Claude Design（claude.ai/design）**：mp（小程序）+ admin 的视觉/换肤/设计 token 一律以 Claude Design 导出为准。方案优先用 Claude Design 出 mockup；没有 Claude Design 覆盖的用 HTML 草案兜底。
> 判据：负责人 能扫一眼看懂「三个方案分别长啥样、差在哪、各自取舍」= 好单；要他自己脑补差异 = 没写到位。

## 怎么用

- **只对关键页面出方案**，不是每页都出（列表/详情这类通用形态跟着选定方案的规范走即可）。哪些算关键页面由业务边界判断：一级导航主页、高频录入、看板、复杂多步交互。
- **每关键页面出 2-3 个方案**，方案之间要有**实质差异**（信息架构 / 布局密度 / 交互范式），不是同一版换个颜色。
- **产出优先 Claude Design mockup**（claude.ai/design 出图，贴截图 + 链接）；Claude Design 覆盖不到的场景用 HTML 草案（贴截图 + 草案文件路径）。两种都行，一页里注明用的哪种。
- **每方案必写取舍**（这方案强在哪、弱在哪、适合什么场景）—— 没取舍 负责人 没法选。
- **留 负责人 选定位**：负责人 填「选定方案 __ + 一句反馈」。选定后此页锁定视觉基准，才进 ticket 拆解。
- stack-agnostic：下面占位符 `<页面>` `<方案定位>` `<差异点>` 按项目实际替换。

## 出方案后怎么走（衔接 §2 交付门 + 编排层）

1. 每个关键页面出一份，落到 `doc/design-options/<页面>.md`，登记进 `_manifest.json`（`needs_human.route=owner` + `why="设计方案待选"`）—— 视觉拍板归 负责人，不是甲方。
2. 编排层据此微信叫 负责人 审：甩 Claude Design 链接 / 草案截图过目 → 负责人 在「负责人 选定」位填方案 + 反馈。
3. 负责人 选定 → 该页视觉锁为基准（进 UI 索引作为该页组件形态的权威依据）→ **才拆 ticket**。混选（如「A 布局 + B 抽屉」）也算选定，按合并版锁。
4. 全部关键页面选定后，`status=done` 进拆 ticket 环节。**任一关键页面没选定 → 不进 ticket 拆解**（视觉未定不拆）。
