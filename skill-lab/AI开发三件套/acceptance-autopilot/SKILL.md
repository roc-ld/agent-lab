# ③ 验收 / acceptance-autopilot（工人技能 · 三件套之三）

> **三件套里的位置**：⓪[fangan](../fangan/SKILL.md) → ①[xuqiu](../xuqiu/SKILL.md) → ②[zhixing](../zhixing/SKILL.md) → **③本 skill**。
> **本 skill 是骨架不是实现**：①②③ 里只有 ③ 天然是项目级的（"问题从哪来、怎么验、写到哪"每个项目都不一样）。
> 本文把**可复用的机制**固定下来，把**可变的部分**全部收进一份 `autopilot.config.yaml`。
> 本骨架提炼自一个已跑过 700+ 条真实验收问题的项目级实现；该实现涉及客户业务，未包含在资源包内。

## 0. 与 ①② 的根本区别

| | ①② | ③ |
|---|---|---|
| 输入 | 需求文档（一次性、结构化） | **甲方/测试人持续提的问题**（持续、口语化、带截图） |
| 反馈环 | 计划内 | **计划外**——由甲方提问题触发，不随 ② 完工自动开始 |
| 判据 | 机器闸门（lint） | **真机/端到端证据** + 干净 QA 对抗验收 |
| 对外写回 | 无 | **有**（写回甲方的问题表）→ 必须人闸 |

**最重要的一条**：③ 是唯一有 **outward-facing 写回** 的环节。假装"AI 修好了"写回去，
比不写回去危险得多——甲方会按你写的去复测，然后发现没好。

## 1. 契约

| | 约定 |
|---|---|
| **cwd** | 项目根（不是 `<ws>`；验收期 ①② 的文档一般不参与） |
| **输入** | 甲方的问题表（在线表格 / 群里贴的截图）+ 项目源码 + 可跑的测试环境 |
| **产出** | 台账（`<ledger_dir>/_ledger-<sheet>.json`）+ 每条的 `evidence` + `audit` + 写回表 |
| **何时停手** | 取不到截图 / 台账校验反复不齐 / 同主题 ≥8 条仍待拍板 / 高风险三类改动没拿到明确拍板 |
| **唯一对外通道** | `writeback`（分级闸，见 §5） |

## 2. 四门一策（本 skill 的骨架）

**每一道门都是程序闸门**：`gate.py <子命令>` 退出码 ≠ 0 就 STOP，不靠文字自觉。
骨架的项目实现建议写成项目内的 `doc/test/_autopilot/lib/gate.py`（门）与 `ledger.py`（台账）。

```
① 取图门   gate.py image <sheet> <行>
           有图必须拿到文件才动手；拿不到 → 自动记 blocked_image + exit 2 挂起
           ⚠️ 没有截图就凭文字猜，是这一层最贵的错误

② 复述门   写复述卡落台账 → gate.py restate-check <sheet> <行>
           过了才准动代码。复述卡必须含"截图里出现、描述里没有"的具体内容
           （防复读甲方原话交差）

②b 口径门 restate-check 内嵌
           动码前先查「现行口径是什么」。命中而未引用 → exit 2
           没有现行口径的 → 先登记 clarify（带 fallback），按 fallback 先做，不停机
           ★ 这条防的是「把待拍板写进备注里，然后没人再读」

③ 验证门   落台账时的**硬校验**（虚报状态物理写不进）
           无截图的 verified_*、无复现证据的 not_a_bug → 直接抛异常

④ 验收门   gate.py audit-coverage
           **每批修复完成后必跑一支干净独立 QA subagent 逐个对抗验收**
           主任务方自测 ≠ 验过：只有 fresh-context、默认怀疑的 agent
           拿真实接口/DB/代码证据 refute 一遍、PASS 才算
           verdict=PASS(independent) 缺失 → 不许写「已处理」

⑤ 一策     分级写回（§5）——Tier-1 进度戳自动 / Tier-2 结论仍人闸
```

## 3. stage 状态机（台账唯一合法值）

自由文案写不进台账——这是防"含糊糊弄"的第一道结构。

| stage | 定义 | 进入条件（强制） |
|---|---|---|
| `blocked_image` | 取不到截图挂起 | 取图门自动打 |
| `triaged` | 只分析没动手 | — |
| `clarify` | 待甲方/人拍板 | **必须先登记** question + fallback，台账挂 decision id |
| `wont_do` | 决定不做 | — |
| `not_a_bug` | 现状正确 | **必须带复现证据**（真实接口/SQL/真机走查；静态读码不算） |
| `fixing` | 动手中 | **必须先过复述门** |
| `fixed_local` | 源码改了未验 | — |
| `verified_e2e` | 端到端验过 | `evidence.channel` + 证据 |
| `verified_device` | 端侧真机证据在手 | **证据文件必须真实存在**（死路径写不进） |
| `deployed` | 已推环境 | 同 verified 要求 |
| `confirmed` | 写回后 N 天无再提 | 机器扫描判定 |
| `regressed` | 再提/回归 | 机器扫描判定；再提 ≥2 次 = 顽固，强制根因调研 + 全量独立验收 |

细节文案放 `stage_note`，**不占 stage**。

## 4. 干净 QA 对抗验收（④门，不可选）

**为什么不可选**：主任务方（改代码的人）有确认偏差——知道自己改了啥，容易只验"我改的那处生效"，
漏验"需求是否真达成 / 有没只改一半 / 平台差异 / 数据是否真落库"。

**怎么跑**：一批的**每一条**（不只顽固行）fan-out，每条一个 fresh-context QA agent：

- prompt 给「问题原文 + 原图 + 我声称的改动 + 改的文件 + after 证据」
- **明确要求它尽力 refute（证伪），默认这条有问题**
- 用真实接口/DB/代码独立核当前状态，**不信主线程的测试结论**
- 输出 `verdict(PASS/FAIL/PARTIAL/NEEDS_VISUAL/NEEDS_CLARIFY) + refutation_attempted + evidence + residual`
- `PASS` 才算真验过；FAIL/PARTIAL → 回去补到 PASS 再写回，**绝不带病标「已处理」**

模板见 `templates/clean-qa-prompt.md`。

> ⚠️ **其他 agent 环境 与 Claude Code 的差异**：Claude Code 可以 `agentType:'qa-reviewer'` 指定专用 agent；
> **其他 agent 环境 的 subagent 没有 agentType**——把 QA 人设与"禁读实现方解释"写进 prompt 正文即可，
> 语义等价（都是 fresh context）。别写 `agentType`，其他 agent 环境 会直接拒绝。

## 5. 分级写回（唯一的对外动作）

**闸的物理形态建议三层**（推荐做法）：① precheck 命令先跑 → ② 写回函数内 in-process 闸
→ ③ PreToolUse hook 拦裸写命令 → ④ 写后回读校验。

| Tier | 内容 | 条件 | 谁触发 |
|---|---|---|---|
| **Tier-1 进度戳** | 白名单模板：「已受理，处理中(M/D)」「待口径确认：<一句话>」「待真机测试：<测什么>」。**禁词表**：已处理/已修复/已解决/已完成 | 一次性授权标记存在 | AI 批量打 |
| **Tier-2 结论备注** | 「已处理：<一句话>」等结论 | stage ∈ {verified_e2e, verified_device, deployed} **且当日授权标记** **且 `audit.verdict=PASS(independent)`** | 人过目后 AI 写 |

> **marker 语义 = 人的动作**。AI **不自行**创建授权标记（`touch` 一下自我授权就把闸拆了）。
> 这道闸防的是"误写/漏 marker"，不是对抗蓄意自授——那靠人过目。

**备注怎么写**：短（建议 200-300 字硬上限 360）、**绝不带换行**（实测带 `\n` 写进去当时读得到、事后那格变空——
是最难发现的一种失败）、只装三样：**结论一句 + 取舍/待定一句 + 复测提示一句**。
写完**必须换一条独立路径回读复核**（实测某些在线表格单点回读会把有内容的格读成空，拿它当验证会得出反的结论）。

## 6. 项目的可变部分 → 全部进 `autopilot.config.yaml`

**新项目照 `templates/autopilot.config.yaml` 填一份，不要改本 SKILL.md。**
需要项目填的：问题表地址与 sheet 列表、列布局（哪列是 AI 唯一可写列）、
验证通道（每个端用什么证据）、台账目录与路径、授权标记路径、写回阈值、平台坑位引用。

填完的落地形态建议：项目侧 `.claude/skills/<项目>-acceptance/SKILL.md` 只写**项目差异**，
机制部分直接引用本 skill——**别再复制一份正文**（镜像必腐烂，已有实例）。

## 7. 常驻风险（本 skill 拦不住的，诚实列出）

| 风险 | 为什么拦不住 | 兜底 |
|---|---|---|
| 甲方描述本身有歧义 | 文本层无解 | 复述门 + clarify 登记 |
| 平台专有行为（H5 假绿、真机才现） | 只有真机/模拟器能验 | 项目配置里声明"必须真机"的模式清单 |
| 审美体感（间距/配色） | 模型天花板 | 批式人工抽验 + 抽验菜单 |
| 硬件长尾（相机/NFC/GPS） | 模拟器无能为力 | 明确备注「需人力真机（具体硬件）」 |
| 台账编造证据 | 程序只能验"文件存在" | 干净 QA 复核 + 死路径拒绝写入 |

## 8. 反模式（会直接毁掉这套机制）

1. ❌ **台账写自由文案 stage** → 一律枚举，写不进才对
2. ❌ **没有截图就按文字猜着改** → 取图门存在的全部理由
3. ❌ **主任务方自测当验收** → ④门存在的全部理由
4. ❌ **AI 自己 `touch` 授权标记** → 闸等于没有
5. ❌ **把「待拍板」只写进备注** → 必须有落点（decision 台账），否则永远没人再读
6. ❌ **改口径不改旧条** → 新口径 supersede 旧条，并反查按旧口径做过的行
7. ❌ **一条坏条目毒化整张台账** → 只强校验本次新增/变更，历史失效条目降级警告
8. ❌ **手工镜像机制正文到项目 skill** → 只写差异 + 引用
